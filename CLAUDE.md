# CLAUDE.md — Waveframe Architecture & Development Guidelines

## Project Context & Environment
- **Application Name:** Waveframe (renamed from "SoundForge" — trademark conflict with MAGIX/Boris FX "Sound Forge")
- **Target Platform:** Windows 10 / 11 (x64) desktop only
- **Framework:** Electron (main + sandboxed renderer + preload bridge), vanilla JS/HTML/CSS — no frontend framework, no bundler
- **Run Command:** `./node_modules/.bin/electron.cmd .` (or `Run Waveframe.bat`)
- **Build Command:** `npm run dist` (electron-builder, `portable` + `nsis` targets) — verified working end-to-end (portable `.exe` launches cleanly, `music-metadata`'s asarUnpack resolves correctly at runtime)
- **Roadmap:** see `WAVEFRAME_ROADMAP.md` in this same folder for the phased backlog and what's done/pending
- **QA process:** at the end of each Phase in the roadmap, bump the version in `package.json` (and the Help window's changelog) and run through `WAVEFRAME_QA_CHECKLIST.md` in full before considering that Phase done

## Execution Rules & Directives

1. **Never use inline `style="..."` HTML attributes.** The app's CSP is `style-src 'self'`; any inline style attribute (even `display:none` or a CSS custom property like `--pct:0`) is silently blocked and breaks the element. JS-driven `element.style.x = y` / `element.style.setProperty(...)` mutations are fine — only the HTML attribute form is blocked. Use a class toggle or a JS-set property instead.
2. **`window.prompt()` and `window.alert()` do not work in this renderer.** Use the existing `showInputDialog(title, initial)` / `showAlertDialog(title, message)` helpers in `renderer/app.js` (built specifically to replace them) for any new input/confirmation UI.
3. **A pure-ESM npm dependency (like `music-metadata`) cannot be `require()`'d from the CommonJS main process.** Use `await import('pkg-name')` inside an async IPC handler, and add the package **and its full transitive dependency tree** to `build.asarUnpack` in `package.json` (see the existing list) or it will fail to resolve once packaged with `npm run dist`.
4. **Never perform blind screen-coordinate mouse automation** (PowerShell `SetCursorPos`/`mouse_event`, or equivalent) to test this app. A prior blind click brought an unrelated open application (the user's ERP software) to the foreground instead of the Waveframe test window. Verify a change by: `node --check` on every touched JS file, relaunching (`taskkill //F //IM electron.exe` then relaunch), reading `run.log` for errors, and confirming the window via `Get-Process | Where MainWindowTitle -eq 'Waveframe'` — screenshots only after focus is confirmed by title/handle, never by guessed coordinates.
5. **Secondary windows (Help, and any future ones) must follow the active skin/theme.** Pass the current theme via a `?theme=` query string on `loadFile()` so it applies before first paint (see `renderer/theme-init.js`), and forward live changes through the `theme:changed` → `theme:sync` IPC pair already wired in `main.js`.
6. **All Greek UI strings must be pure Greek — no stray English terms** (e.g. "Dependencies"). Every user-facing string goes through `renderer/i18n.js`'s `data-i18n` system; never hardcode a label directly in HTML/JS.
7. **Any new localStorage key must be prefixed `waveframe.`** — the Backup & Cloud Sync feature (Settings tab) exports/imports every `waveframe.*` key generically; an unprefixed key silently won't be backed up.
8. **Icons for OS-level UI (taskbar thumbbar, etc.) are drawn on an offscreen `<canvas>` in the renderer and sent to main via IPC as data URLs** (`nativeImage.createFromDataURL`) — this project has no image-asset build pipeline (no `sharp`/`png-to-ico` installed as dependencies; the one earlier icon-generation script was ad hoc and removed). Prefer the canvas approach over adding new binary asset files or new npm deps for small UI glyphs.
9. **The main window is resizable/maximizable** (`minWidth`/`minHeight` floor at 1180×760). Any new fixed-pixel layout assumption (a hardcoded `width`/`height` in CSS, or a canvas sized once from a constant) will look broken when the window is resized/maximized — size from `window.innerWidth/innerHeight` or `getBoundingClientRect()` and listen for `resize` where relevant, per `renderer/backgrounds.js`.
10. **Do not build a YouTube / YouTube Music downloader-and-convert feature into the shipped app.** Downloading and locally converting copyrighted streaming audio without the rights holder's permission is a ToS violation and a copyright risk once this app is distributed to end users; no GitHub library changes that legal reality. If asked again, only add generic direct-audio-file-URL loading (already supported), and point the user at running `yt-dlp` themselves outside the app as a separate, user-operated tool if they want that workflow for personal use — never wire it in as a built-in one-click app feature.
11. **Waveframe does not bundle its own FFmpeg binary — do not reintroduce the `ffmpeg-static` npm dependency.** That package (and the Windows binary it downloads) is GPL-3.0-or-later, which triggers real source-distribution obligations once this app is distributed. Surveying real-world precedent (other Electron/Qt/.NET/Python audio-player projects on GitHub that bundle FFmpeg) confirmed the standard way apps stay proprietary/closed without those obligations is to use an **LGPL-only** FFmpeg build — the same pattern this project now follows: `resolveFfmpegPath()` in `main.js` checks, in order, (1) an `ffmpeg` already on the user's system `PATH` (e.g. a codec pack — never assume this covers Waveframe's own distribution obligations for what *it* bundles, it's just a nicer first choice when available), then (2) a copy downloaded on demand from BtbN's `win64-lgpl.zip` build (not `-gpl.zip`). Waveframe only needs audio codecs (mp3/flac/vorbis/aac/opus/wma), none of which require GPL-only components, so this has no functional downside. Reflect any change here in the Help window's "Άδεια χρήσης" tab too.

12. **Opus export always forces 48kHz**, regardless of the chosen quality tier's `sampleRate`. `libopus` only supports 8/12/16/24/48kHz — the Low (22050Hz) and Medium (44100Hz) quality tiers used to make Opus exports fail outright (confirmed with a real downloaded MP3 test file: ffmpeg errored "Specified sample rate 44100 is not supported by the libopus encoder" and wrote a 0-byte file). See the `effectiveRate` override in `main.js`'s `export:save` handler — do not remove it or reintroduce a raw `sampleRate` pass-through to `-ar` for Opus. **Opus also has its own bitrate ladder** (`OPUS_BITRATES` in `renderer/app.js`: 64/96/160kbps for Low/Medium/High) instead of the shared `QUALITY` bitrates (96/128/320) — Opus is far more efficient per-bit than MP3/AAC, so reusing the same numbers would be wasteful.
13. **The default export destination folder is the OS Music folder** (`app.getPath('music')`, exposed to the renderer as `window.waveframe.musicPath` via a sync IPC call in preload, same pattern as `version`), used only when the user hasn't explicitly picked a folder (`localStorage.getItem('waveframe.destFolder')` is empty). Once the user picks a folder via "Επιλογή", that choice persists and overrides the default as before.
14. **Installer EULA pattern modeled on the user's own `GearWin` project** (github.com/giorstergiopoulos-design/GearWin, an Inno Setup installer with a mandatory per-language license page). electron-builder's NSIS target supports the same idea natively: `build/license_<lang>.txt` per supported UI language (plus a bare `build/license.txt` fallback) is auto-detected by filename convention — no explicit `license` key needed in `package.json`. All 20 current languages have a license file. `nsis.multiLanguageInstaller: true` + `oneClick: false` gives the full wizard (license page, install-directory choice, shortcuts) rather than a silent one-click install. Keep every language's license file in sync if the bundled dependencies/their licenses ever change (currently: Electron/music-metadata/adm-zip = MIT, FFmpeg = LGPL per rule 11).
15. **New UI strings go into the `el` (Greek) i18n block only, as they're added** — the full translation pass into the other 19 languages is a deliberate, separate batch done once at the end of each roadmap Phase (explicit user preference, to avoid context-switching into translation mode for every small feature). Before calling a Phase done, grep for any `el`-only keys and translate them everywhere. When generating translated strings programmatically (e.g. a Node script building i18n.js blocks), never interpolate a value directly into a hardcoded `'...'` template — any apostrophe in the translated text (e.g. French "l'application", "You're") breaks the generated JS string. Use `JSON.stringify(value)` for the literal, or branch per-string between `'...'`/`"..."` based on content.
16. **`npm run smoke-test`** (`smoke-test.js`) launches the app, waits ~4s, checks it didn't crash and logged no errors, then cleans up — use this instead of a manual relaunch for routine verification. On Windows, `node_modules/.bin/electron.cmd` is a shell shim, not a real executable: it must be spawned via `cmd.exe /c`, which means the real `electron.exe` ends up as a **grandchild** of the Node process running the test. Plain `child.kill()` only kills the `cmd.exe` wrapper and leaves `electron.exe` running (confirmed: an early version of this script leaked 5 orphaned `electron.exe` processes per run) — always clean up via `taskkill /pid <pid> /T /F` (kill the whole process tree) on Windows instead.

## Verification Checklist (before saying a change is done)
- [ ] `node --check` on every touched `.js` file after every meaningful edit — this is the primary interim verification
- [ ] **Do not relaunch the app after every small change.** Relaunch once, as a single final check at the end of a Phase (per `WAVEFRAME_ROADMAP.md`) — repeated launches during a single phase leave orphaned/zombie `electron.exe` processes that `taskkill` can't always clean up (observed: some survive with "access denied" even under `taskkill //F`), and the user has asked for this explicitly.
- [ ] At that one relaunch: confirm `run.log` has no new errors, and confirm via `Get-Process` that a `Waveframe`-titled window exists (an unrelated stale/zombie process from earlier in the session may also still be listed — that's pre-existing noise, not a new bug, and not worth chasing further)
- [ ] If UI changed: state clearly that a click-through visual check was or wasn't possible (simulated OS clicks may be denied), rather than claiming an unverified visual result works
